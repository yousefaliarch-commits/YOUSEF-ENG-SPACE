# Security and media — the rules every change keeps

Phase 1 of the transformation plan. Steps 1.2 (database armor) and 1.3 (media privacy) are in place; 1.1, 1.4 and 1.5 follow.
Everything below is pinned by tests: `supabase/tests/database/18_security_invariants.test.sql`, `19_media_privacy.test.sql`,
`tests/upload-media.test.ts`, `tests/compress.test.ts`, the cloud suite and `e2e/media.spec.ts`.

## Database: default deny (migration 24)
- **No function is callable by `PUBLIC` / `anon`**, and no function by `authenticated` unless a migration says
  `grant execute on function … to authenticated` explicitly. The Postgres default (EXECUTE to PUBLIC on every new function) is
  revoked for role `postgres`; the invariants suite creates a function and a table and checks they come out closed.
- `anon` holds nothing on any public table; `authenticated` never holds TRUNCATE / TRIGGER / REFERENCES (none is covered by RLS).
- Every public table has RLS; every security-definer function pins `search_path`. A migration that breaks either fails CI.
- pgTAP helpers created with `create function pg_temp.…` need `grant execute … to public` (default deny covers them too).

## Writes members make
- **Rate limits** (`private.rate_limit`, trigger `private.limit_writes(bucket, burst, window, daily)`): posts 8 / 10 min · 40 / day;
  comments 20 / 10 min; messages 30 / 5 min; reviews 3 / h; jobs 5 / h; tickets 3 / h; ticket messages 20 / 10 min; reports 10 / h.
  Staff and the service role are exempt. A refusal is SQLSTATE 54000 «rate limited» (the app: «أرسلت كثيرًا في وقت قصير»).
  A SQL session may `set local engspace.rate_limits = 'off'` (tests); the Data API cannot.
- **Role** (engineer / supervisor / hr / owner decides money access): free while completing the profile; afterwards once in 30 days,
  verification dropped, audited by mod_ref (`private.role_guard`). Onboarding cannot be reopened. Staff changing someone else's role
  (`admin_set_account`) are not limited.
- **Job views** count once per member per job per day, signed-in only.
- **jsonb caps**: `posts.data` 16 KB (only `reveal`, `image`, `vote`, `poll` survive), `comments.data` and `company_reviews.data` 4 KB,
  `profiles.settings` 4 KB, each `member_state` value 1 MB, at most 40 state keys per member.

## Images (migration 25, `supabase/functions/upload-media`)
```
phone: pick → src/lib/compress.ts (≤ 1600 px, orientation applied, WebP / JPEG, 150–250 KB, no metadata)
  → POST /functions/v1/upload-media  (member JWT, x-media-kind)
      reads the real format + size from the bytes · refuses PNG / SVG / animated / oversized · strips EXIF / XMP / comments again
      media_register (rate limit 30 / 10 min · 300 / day · 10 avatars / day · 100 MB per member) → stores with the service role
  → { path } → the app writes the row that refers to it
```
| Kind | Bucket | Path | Who reads it |
|---|---|---|---|
| post | `media` (public) | `p/<random>.webp` | through `post_media()` only — see below |
| avatar | `media` (public) | `a/<random>.webp` | anyone who sees a public item (snapshot `photo`) |
| support | `support` (private) | `<member>/<random>.webp` | the member and staff (signed URL) |
| verification | `verification` (private) | `<member>/<random>.webp` | the member and staff; deleted at decision, 7 days max |
| inspection | `inspections` (private) | `<member>/<random>.webp` | the member only (signed URL) |

- **No account id in anything readable.** Members cannot write to the `media` bucket at all. A post keeps only the image's geometry,
  colour and alt text in `posts.data`; the path lives in `public.post_images` (no member policy). `post_media(ids)` hands a path only
  to those allowed to see the image.
- **Payslip rule, on the server (strict default).** Engineers, the author and staff see a post image at once. HR, owner and supervisor
  accounts see it only after staff review it as clean (Admin → «مراجعة الصور», `staff_review_image`, audited). The phone's own
  reading (`client_scan`) is a hint for staff, never a decision.
- **Profile photos** must be the member's own avatar upload (`private.photo_guard`).
- **The janitor** (pg_cron `engspace-media-janitor` every 10 minutes → `upload-media` with `x-media-secret`) moves files from before
  Phase 1.3 (`media/<account id>/…`) to random names, deletes uploads never used (24 h), images of deleted posts, and every upload of a
  deleted account. `MEDIA_SECRET` is generated by the Deploy database workflow on each deploy and written to the function and Vault.
- Inspection photos are removed by their owner (`x-media-action: remove`, checked by `media_removable`) when a photo or an
  inspection is deleted.

## Taking photos in the phone apps (native line 2)
v0.26.0 crashed on «التقاط صورة»: iOS ends an app that asks for the camera without `NSCameraUsageDescription` (Info.plist had no
privacy texts at all), and on Android a web view page process that dies (memory, or reclaimed while the camera app is in front) took
the whole app with it. Now:
```
tap «صورة» / «إضافة صورة» / «تغيير صورة الحساب» / «إرفاق صورة»
  browser            → the file input, as before
  phone app          → chooser (src/lib/media.tsx): «التقاط صورة» · «اختيار من الصور»
     camera          → src/native/camera.ts: checkPermissions → requestPermissions(["camera"]) only if not asked yet → getPhoto(Camera)
                        denied → a note saying where to allow it (Settings → EngSpace → Camera); the camera never opens
     gallery         → getPhoto(Photos) (no camera permission; Android's system photo picker)
     either          → the plugin scales to ≤ 1600 px with the orientation applied (resultType uri) → File → compress.ts → upload-media
     plugin fails    → the plain input takes over (capture="environment" for the camera), offered as a button, and for the rest of the run
```
- **iOS** `Info.plist`: `NSCameraUsageDescription`, `NSPhotoLibraryUsageDescription`, `NSPhotoLibraryAddUsageDescription` (Arabic, then English).
- **Android** manifest: `CAMERA` (asked when the camera is chosen — with it declared, nothing may start the camera before it is granted;
  the plugin and the web view's capture path both ask first), `android.hardware.camera` not required, `<queries>` for `IMAGE_CAPTURE`
  (Android 11+ hides the camera app otherwise), FileProvider paths for `getExternalFilesDir` and the cache.
- **MainActivity** handles `onRenderProcessGone`: the dead web view is removed and destroyed and the screen rebuilt (`recreate()`); three
  losses within a minute end quietly instead of looping. iOS already reloads the web view itself (Capacitor).
- **Memory**: `compress.ts` reads the size and EXIF orientation from the file header and asks `createImageBitmap` for the scaled picture
  (`resizeWidth`), then releases the decoded source before the encode loop — a 50 MP photo no longer sits in the page process at full size.
- Android keeps the camera app's full-size original in the app's private Pictures folder: `sweepCaptures()` deletes those older than a day
  at launch.
- Never `Camera.getPhoto` anywhere but `src/native/camera.ts` (pinned by `tests/native-camera-config.test.ts`); the plugin's logic is pinned by
  `tests/camera.test.ts`, the chooser by `e2e/media.spec.ts` through the development-only `window.__engspaceCamera` stand-in.

## Local development
`npm run db:start` then `npm run db:functions` (serves `upload-media` with `supabase/functions/local.env` — a development-only secret).
`npm run test:cloud` needs both. The function uses plain `fetch` against the REST endpoints (`_shared/rest.ts`) — no npm download
at cold start; its logic lives in `_shared/media.ts` and `_shared/media-handler.ts` so Vitest drives it with a fake client.
